## 0.5 ★ P0.5:选帧对照与两个关键认知

### 首轮结果(种子有 bug,已作废,数据存 `traj_randomB2_seedbug`)

配对 116 题:recent-B2 36(31.0%) vs random-B2 34(29.3%),
列联表 都成功25 / 仅recent11 / 仅random9 / 都失败71,
**+1.7pp,McNemar 精确检验 p=0.82 不显著**。

### 缺陷一(致命,已修):随机种子退化

`seed = hash((seed, step, total))` 而调用处 `step == total`,于是
**每个历史长度只对应唯一一种选择** —— 全部 117 题、所有 episode,
只要 `total=6` 就一律选 `[0,2,6]`。这不是随机策略,而是"每步数一个固定
模式",人为压低 random 臂方差。修法:把**任务指令**混入种子,并改用
`hashlib`(内置 `hash` 受 `PYTHONHASHSEED` 随机化,跨进程不可复现)。
修复验收(真实运行中,非单测):同一 `total=8` 下出现 **19 种**不同帧组合,
旧实现只有 1 种。recent 分支不走随机路径且 parity 88 用例 0 失配,故复用。

### 缺陷二(非 bug,是**认知**):文本折叠削弱对照强度

MobileWorld 与 AndroidWorld **不同构**,这点决定实验怎么解读:

* AndroidWorld:`cut_current_messages` 把旧帧**图像清空**,信息真丢失;
* MobileWorld:未选中的帧被渲染为文字
  `Step<N>: <conclusion>  Tool response: <...>` **完整保留**。

因此两臂 prompt 里全部 50 步的语义描述**完全相同**,唯一差别是"哪 2 步
额外附了像素"。模型靠当前帧 + 完整文字历史即可决策,历史图像的边际
贡献被压到噪声量级 —— 这很可能是与用户 7 月自建 runner(+6.84pp,
p=0.0039)结论相反的**结构性原因**,而非当时结论有误。

**用户裁定(2026-08-24)**:动作 summary 本就应当保留,该设计正确,
不做"无文字兜底"的变体。故本课题在 MobileWorld 上要证明的命题相应收紧:
**在已有完整文字历史的前提下,选哪些帧提供像素是否仍带来增益。**

### 干预面(唯一改动点,88 用例 parity 保证)

把官方硬编码的连续窗口 `user(img[t])→assistant[t]→user(img[t+1])→…`
参数化为**任意图像索引集合 S**(必含当前帧);`S=[t..total]` 时逐字节
退化为官方行为。预算 `B = history_n - 1`,由 `CC_HISTORY_N` 注入
(官方无 CLI 开关)。断言口径:「图像索引序列 + 文本折叠索引序列」
唯一决定 messages,两序列相同即等价于逐字节相同。

## 2. ★ 用户当日质询的三项违规(全部属实)

### 2.2 匿名配置是空指针,`VLLM::EngineCore` 裸奔 14 小时

容器设了 `PYTHONPATH=/data/pyshim`,但**该目录从未创建** —— 全局规则要求的
进程名压平从头到尾没生效。两层修复:

1. 建 `pyshim/sitecustomize.py`,解释器启动阶段(框架导入前)劫持
   `setproctitle` 强制为 `python`;
2. 入口从 `vllm serve` 改为 `python3 -m vllm.entrypoints.openai.api_server`
   —— **`setproctitle` 改不了 `/proc/pid/comm`**,comm 取自 exec 的可执行名,
   这层此前没意识到。

验收:`nvidia-smi --query-compute-apps=pid,process_name` 输出 `python`。

### 2.3 并发被容器数卡死

官方 runner `n_jobs=min(max_concurrency, len(aw_urls))`,我只起 8 台 env 容器
且未传 `--max-concurrency` → 8 路串行。已扩到 **32 台 / 并发 32**。

## 3. ★ 自我推翻:加卡是错的方向(实测数据)

扩并发后实测 vLLM:**generation 25-41 tokens/s、`Running: 0`、
5 分钟 149 请求(0.5 req/s)**。单张 H200 跑 8B 是数千 tokens/s 量级 →
**GPU 实际负载 <1%**。每步约 64 秒中推理不足 1 秒,其余全在 emulator
步进/截图/`step_wait_time=3`。

据此把 DP=2 **缩回单卡,GPU7 归还**。结论写死:
**闭环 GUI 评测的 GPU 是次要瓶颈,靠加卡拉不动利用率;
按全局规则"减少占卡数优先于保持高卡数低利用率"处理。**
(注:全局规则的 80% 利用率硬指标对这类 env-bound 任务不可达,
不应通过占更多卡去"达标"。)
