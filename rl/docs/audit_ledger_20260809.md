## 0. 一句话现状

**四次迭代后拿到第一个正向但不显著的结果**:监督训练的 selector 在困难态上
32.6%,显著优于随机初始化头(20.3%,p=0.000),但**相对部署基线 recent-2
(30.8%)只高 1.8pp,p=0.188 不显著**。上界(枚举 oracle)是 49.1%。
下一个决策点:是加训练量、改架构,还是先做闭环检验。

**⚠️ 与我几小时前口头汇报的差异**:那时用 205 态样本,learned 36.1% /
recent 32.2%,差距 3.9pp。扩到 838 态后差距**收窄到 1.8pp**,捕获率从
我说的 23% 降到约 9%。**以本文档为准。**

## 1. 三十秒背景

**问题**:GUI agent 每步只能带 B=2 张历史截图进 prompt(上下文有限)。
部署默认取"最近 2 张"。问:**换一种选法能不能更好?**

**为什么值得答**:如果不能,CausalCache 的核心主张(固定预算内重分配)
就不成立;如果能但学不出来,那是学习问题;两者的应对完全不同。

**成功长什么样**:学出来的 selector 在**部署口径**下显著优于 recent-2。

## 4. 实验台账(时间倒序)

### v4 —— 监督排序(2026-08-09)

- **假设**:v3 失败是因为"训 `log p` 评 `argmax`"两者脱钩;若换成与评测
  同源的目标(把能做对的子集排前面),应能学到有用的选帧。
- **现象**:训练 2022 态 / 252 优化步 / 16176 成对样本,成对损失
  0.791→0.716,留出集排序准确率 **0.5828**(0.5=随机)。
  同口径评测 838 个困难态:learned **32.6%** / init **20.3%** /
  recent-2 **30.8%** / 随机-2 **24.8%**。
  learned vs init **+103,155 胜 52 负,p=0.000**;
  learned vs recent **+15,64 胜 49 负,p=0.188**。
  选帧重合:learned==init 仅 5%,learned==recent 26%。
- **判断**:**已证实** —— 目标函数换掉后确实学到了可迁移能力(vs init 的
  p=0.000 和留出集 0.583 是两个独立证据)。**同时证实** v3 的病因诊断:
  同架构、同初始头、同数据,只换目标,20.3%→32.6%。
  **未证实** —— 是否真的优于 recent-2(p=0.188)。
- **改动**:新增 `rl/code/scripts/train_selector_supervised.py`(a31577a);
  评测脚本加分片以扩样本(7476323)。
- **结果**:见上。捕获率 ≈ (32.6−30.8)/(49.1−30.8) ≈ **9%**
  ⚠️ 跨样本计算,见 §3 缺陷。
- **去留**:**保留**。这是目前唯一学到东西的配置。

### v3 —— 离线步级 RL(2026-08-08)

- **假设**:把奖励从"整条 episode 成败"换成"每步的 `log p(gold action)`",
  信用分配从 670:1 降到 2:1,应能学出有用的 selector。
- **现象**:3000 态、**750 优化步**、位移 **1.557**、熵 3.94→2.32 ——
  优化机制完全奏效。但评测 200 困难态:learned **21.5%** vs init 23.0%
  (p=0.701,**无收益**)vs recent 32.5%(p=0.002,**显著更差**)。
  **learned 与 init 选帧仅 13% 重合** —— 行为大改,成绩不变。
- **判断**:**已证实"训动了但没学到"**(与 v1 的"没训动"是不同病因)。
  **推测(后被 v4 证实)**:`log p` 可以大涨而 argmax 一次不翻,
  连续目标与离散指标脱钩。
- **改动**:`train_step_level.py`(score-function 绕过选帧离散 + HGKV 可导
  SFT);新增同口径判据脚本 `rl_selector_eval.py`。
- **结果**:见上。
- **去留**:**回退**目标函数,保留训练框架(v4 复用了它的索引遍与架构)。

### 枚举 oracle —— 冻结 policy + 只换帧(2026-08-08~09)

- **假设**:冻结 policy 不动,只把历史帧换成最优的,步级正确率能提多少?
  这是"选择本身值多少"的干净度量,也是所有方法的上界标尺。
- **现象**:5303 个唯一态(可用 5335,覆盖 99.4%),三方并行(h00 3 卡 /
  h01 2 卡 / tilde 8 卡)。**困难态分层(2547 态)**:
  oracle **49.1%** / recent-2 **28.4%** / 随机-2 **22.9%**。
  全体分层:easy 53.0% / **winnable 22.7%(1204 态)** / hopeless 24.3%。
  winnable 内正确子集占比中位 37.9%;承载帧分析显示正确子集**集中**在
  少数关键帧(最强帧携带率比基准高 +33.4pp)。
- **判断**:**已证实头寸真实存在**(+20.7pp,n=2547)。
  **已证伪**归档里那条 AndroidWorld 警示("喂正确图 vs 打乱图差异≈0")
  在桌面数据上不复现 —— 帧内容确实影响动作。
  公平对照 recent−随机 = **+5.6pp**(p 由 n=2547 支撑):
  "选最近两张"只比随便选好一点点。
- **改动**:`rl_oracle_enumerate.py` + `rl_oracle_analyze.py`;
  契约 `oracle_selection_contract.md`(74e8af8 起)。
- **结果**:产出 1204 个 winnable 态作为 v4 的监督训练集。
- **去留**:**保留**,作为所有后续方法的分母。

### v2 —— OSWorld 闭环 RL,修 lr(2026-08-08)

- **假设**:v1 失败是因为学习率过小导致参数根本没更新。
- **现象**:selector lr 1e-4→1e-3、LoRA lr 1e-5→1e-4、grad_accum 8→4 后,
  **iter-1 单迭代位移 0.104**(v1 二十迭代累计才 0.044),
  iter-2 累计位移 0.247、与初始头选择重合率 0.141。
- **判断**:**已证实** lr 是 v1 的病因。
- **改动**:超参 env 化 + 前 3 迭代硬门槛(`selector_drift ≥0.02`)。
- **结果**:门槛通过(0.104/0.242/0.141),iter-6 时用户裁定转向离线,
  **主动终止(非失败)**,权重保留在 h00 `/data04/jaxan/rl2/`。
- **去留**:**归档**。它已完成"证明 lr 修复有效"的使命。

### v1 —— OSWorld 闭环 RL 首版(2026-08-05~08)

- **假设**:用任务成败做奖励、GRPO 联训 selector + HGKV 能提升闭环成功率。
- **现象**:20 迭代、936 episode、双轮 held-out 评测
  RL 81/240 vs recent-B 88/240(Δ=−2.9pp,p=0.345,CI 跨零)。
  **复盘发现两条通道都没训动**:selector 位移 4.4%、与随机初始化头选择
  重合 86.7%;LoRA 的 `lora_b` 范数 0.0399(vs `lora_a` 6.5),
  ΔW 约 0.1% 量级。**总优化步数仅 67 次。**
- **判断**:**已证实为配置失败而非假设失败**。
- **改动**:trainer 加 `selector_drift` / `optimizer_steps` 仪表 —— v1 的
  教训就是这两个数不可见,导致 20 迭代后才靠离线挖掘发现问题。
- **结果**:见上。
- **去留**:**作废**,预注册判据一并作废(它检验的配置不可能产生更新)。

## 8. 追问补录(用户问、已答、写回文档)

### 8.1 25px 容差站不站得住?—— **站不住,需要改**

核实结果(`coordprobe`,6000 样本):目标坐标最大值 **989** → 确认是
**[0,999] 归一化空间**;屏幕 98% 为 1920×1080;**4174/6000(70%)带坐标**,
其余是 `type`/`key`/`terminate`(精确匹配,与容差无关)。

25 在归一空间换算到像素是**各向异性**的:

| 方向 | 换算 |
|---|---|
| 横向 | 25/999 × 1920 = **±48 px** |
| 纵向 | 25/999 × 1080 = **±27 px** |

`action_correct` 算的是归一空间 L2 → 像素空间里是横 48 / 纵 27 的**椭圆**。

**为什么会被审稿人攻击**:菜单行高、列表项高、工具栏按钮高度典型就是
25-35px,**纵向 ±27px 意味着点错一整行仍判对**。在文件浏览器、下拉菜单
这类纵向密集 UI 上,正确率可能被 off-by-one-row 灌水。

**这个值的来历(我的疏忽)**:它是语料构造时用来筛 target-recurrence
正例帧的 `coordinate_tolerance=25`,**不是为评测正确率设计的**;
我直接挪用,没有独立论证。

**为什么不能直接改用"点在元素框内"**:AgentNet 这份 screening manifest
**没有 bbox 字段**(已查 schema),要用元素框得回源数据集取。

**已做的修复**:评测脚本改为**落盘原始预测与 gold**,容差从"生成阶段
烘焙"改成"分析时旋钮"。此前只存布尔值,导致无法事后做敏感性曲线、
只能重跑整轮。后续重跑即可一条命令出 5/10/25/50 的敏感性表 ——
"结论在全区间成立"是应对审稿人的标准答法。

### 8.2 v2 是不是"fallback 到 recent"?—— **不是,但相关观察为真**

iter-6 停机是**用户裁定转向离线**,非自行退化。但 iter-2 时确实观察到
selector 选中帧的归一年龄从初始 0.733 → 0.329(**在往 recent 靠**),
当时标注了两种读法(真最优 / 塌缩),**转向后未再验证,至今无定论**。
参考数据点:v4 学出的头与 recent 的选择重合率仅 **26%**(未塌缩),
成绩却接近 —— 说明"不同的选法可以给出相近成绩"。

### 8.4 新观察:训练损失几乎没降 → 指向特征/容量而非数据量

v4 成对损失 0.791 → **0.716**,而随机水平是 **0.693**(=−log 0.5)。

selector 要"看出来",难得多);② mean-pool 后单层 Linear(4096,1) 容量太小。
