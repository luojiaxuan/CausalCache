# selector 容量与表示能力 外审(2026-08-31)

## 发审前我方判断(先行锁定,防背书)

**用户质疑**:41M 的 selector 根本学不会复杂选帧逻辑,应当与 executor
同量级参数才可行。

**查证后我方结论:质疑方向正确,但根因不是参数量,而且实情更糟。**

实测(`selector/service.py` + `model.py`):

| 项 | 实际值 |
|---|---|
| TinyFrameEncoder | **1.1M**,随机初始化,`.eval()` 冻结,**从不参与训练** |
| FrameSelector 打分头 | **0.1M** |
| 合计 | **1.3M**(而非我先前口径的 41M) |
| selector 的输入 | `convert("L").resize((64,64))` → 4096 个灰度值/帧 |
| GUI 原始截图 | 1080×2400×3 ≈ 7.8M 值 |
| **信息压缩比** | **1898 : 1** |

即 selector 看到的是"GUI 截图压成 64×64 灰度、再过一个**随机权重**的两层
MLP"。该实现是 smoke 阶段的临时件——`model.py` 注释写明"smoke 用
TinyFrameEncoder;规模阶段换 executor 视觉塔 pooled 特征,接口不变",
**但规模阶段从未替换**。

**我方判断**:在此表示下,selector 无法判断"该帧是否含当前决策所需信息"
(文字与图标在 64×64 灰度下已不可辨),至多学到粗糙布局/亮度差异。这可
解释全部既有观察:133 批后行为大改(recency_mass 0.57→0.26)却零性能
变化;learned/recency/S₀ 三臂无显著差异;heldout 效应在 +8.8pp 与 −6.2pp
间摆动(两次均不显著)。**优先级:先修表示,再谈容量。**

## 外审原文(ChatGPT 极高档,临时会话,思考 2m43s + 检索 4 站)

**总判**:"**Yes: representation quality is overwhelmingly the more
plausible bottleneck than selector parameter count.** The new detail
changes my diagnosis substantially."

### (a) 表示 vs 参数量

> "**0.1M 的可训练头不是这里的丑闻,表示才是。**"

你把 1080×2400 RGB 的 GUI 压成 64×64 灰度,再过一个冻结的随机两层 MLP。
**破坏发生在任何可学习组件投票之前**。纵向 2400→64 是 **37.5 倍**压缩,
一个 40-50 px 高的文字元素**只剩约 1-1.3 个像素高**。小标签、开关状态、
图标、选中的 tab、输入的值、通知文本、细微的模态变化——**任务相关的区分
基本全没了**。灰度还额外抹掉颜色编码的状态;若是把 1080×2400 直接拉伸成
正方形 64×64 而不保持长宽比,那是又一层退化。

这对 GUI 尤其致命:近期 GUI-agent 工作反复发现 **OCR、grounding、
UI 元素语义、跨屏理解是核心能力而非细枝末节**。冻结的随机 MLP 恢复不了
其中任何一项。

**它另外指出一个我方未列的瓶颈候选,且排在参数量之前**:
> "**executor 可能根本对你给它哪些历史图不敏感。** 若换历史帧几乎不改变
> executor 的策略,再好的表示也无济于事。**重建之前先测这个。**"

**其排序**:
> 表示/语义信息缺失 ≫ executor 对历史的敏感度 & RL credit assignment
> ≫ 0.1M-vs-更大的 selector 容量

### (b) 用 executor 视觉塔特征后需要多大容量

> "**不,它绝对不需要匹配 executor 的规模。**"

8B executor 要做视觉感知、OCR、grounding、语言理解、规划、动作生成、
世界知识;而 selector 只需解 `s_j = f(task, current state, candidate
frame_j, Δt_j)`,在 ≤50 个候选里选 2 个。
> "**只要输入已含好的语义,这是个很小的决策问题。**"

GUI-Owl-1.5 基于 Qwen3-VL,视觉编码器 27 层、hidden 1152、输出 4096 维
进语言模型——**你是在借用这套昂贵的感知机器,而不是重新学它**。
建议 **1-5M 可训练参数起步,不是 41M,更不是十亿级**。

两条补充设计要求:
1. **不要无差别全局平均池化**:保留每张截图 4-16 个空间池化 token,
   或用一个小的可学 attention pooler;
2. **selector 必须是 query-conditioned**:若它看不到任务指令与当前状态,
   那是另一个根本限制——**"哪张旧帧有用"不是旧帧单独的属性**。

### (c) 便宜且决定性的实验:离线反事实帧效用探针

> "**我不会现在就再训一次 RL。** 在你已有的轨迹上做离线反事实探针。"

1. 从成功轨迹取 300-1000 个状态,每个状态已知参与成功的下一动作;
   选约 8 个历史候选,覆盖近、远、视觉多样的帧;
2. **冻结 executor**,固定一个历史槽(如 t−1),把每个候选 j 换进另一个槽,
   测该动作的**归一化 token 对数概率** u_j。
   > "这只需要 **executor 前向,不需要环境 rollout**。"
3. 问三个问题:
   - **u_j 在不同帧之间有实质差异吗?** 若否,**停** —— executor 不在乎
     你选哪张,selector 几乎没有机会;
   - **max_j u_j 是否显著高于 recency 候选?** 若否,在这些状态上帧选择
     本身就没多少上升空间;
   - **探针能否预测 u_j 的排序?** 用当前随机 64×64 特征训一个同样的小
     排序头,再用 executor 视觉特征训一个同样小的探针,**对比二者**。
   判读:仅后者成功 → **表示瓶颈确认**;两者都成功 → 问题在 RL/credit
   assignment 程序。

### (d) 我可能低估了什么(它给的反面论证)

> "随机特征并非天生无意义。恰当的随机特征映射能保留相似性、近似有用的
> 核,即使随机初始化的网络也能保留可观的低层信息。"

所以当前表示**仍可能**区分:"键盘开/关"、"对话框 vs 全屏"、"以白色为主
的设置页 vs 图像密集页"、"我们导航到了一个视觉上不同的屏幕"、粗略滚动
位置、粗略页面布局、屏幕新颖度。
> "这足以支撑一个规则本质上是'**保留一个结构上不同的旧屏,而不是两张
> 几乎相同的近期屏**'的 selector。**而这很可能正好解释了你学到的策略为何
> 激进地远离 recency。**"

**但重要限定**:随机特征论证成立的前提是**输入仍含相关信号**;它们
不能复活"被平均进几分之一个像素里的文字"。Rahimi-Recht 式随机特征是对
**既有输入几何**的设计性表示;"在残酷摧毁信号之后再套一个任意冻结 MLP"
不会凭空产生语义不变性。

> "所以我不会说这个 stub 学不到任何东西。我会说它**大概率能学到视觉
> 新颖度/时序启发式,却极不适合学习任务条件化的语义记忆检索**。"

### 最强结论(原文加粗)

> "**你并没有真正测试你以为在测试的那个假设。你测的是:一个建立在
> 64×64 灰度随机特征之上的微小 RL 策略,能否在稀疏的 50 步 credit
> assignment 下打败 recency。它不能。这几乎不能说明一个运行在 GUI 语义
> 特征之上的 selector 会怎样。**"

**它的下一步建议**:先跑上面的反事实效用探针;**若确有真实的、依赖帧的
executor 敏感度**,再直接换成 executor 对齐的视觉特征 + 约 1-3M 的打分头,
**在该版本明确显示欠拟合之前,不要动 selector 的规模**。

## 我方裁决

**它同意的**:表示是主瓶颈、参数量不是。与我方发审前判断一致,不展开。

**用户的原始质疑如何裁定**:用户主张"selector 至少要与 executor 同量级
参数量才可行"——**方向(容量/能力不足)正确并直接导致了本次排查,但
具体主张不成立**:外审明确"绝对不需要匹配 executor 规模",借用其视觉塔
特征后 **1-5M 即可**;我方原口径 41M 本身也是错的(实为 1.3M,且其中
1.1M 是冻结不训练的编码器)。

**它反对/补充、我方采纳的(4 条)**:

1. **先测 executor 对历史帧的敏感度,再谈重建**。这是我方完全没有的
   前置问题:若换帧不改变 executor 策略,表示修得再好也没用。它把这一项
   排在参数量之前。
2. **离线反事实帧效用探针**(只需 executor 前向,无需环境 rollout)——
   比我方原计划"改完直接再训一轮 RL"便宜一个量级,且能三路分诊
   (executor 不敏感 / 帧选择无上升空间 / 表示瓶颈)。
3. **保留 4-16 个空间池化 token,不要无差别全局平均**;这一点我方原
   注释("换 executor 视觉塔 pooled 特征")写得太粗,直接全局池化会重蹈
   信息丢失。
4. **selector 必须 query-conditioned**(看得到任务指令与当前状态)。
   **我方当前实现只吃候选帧特征 + 步位置,不含任务与当前状态** ——
   这是第二个结构性缺陷,与表示问题同级。

**它给的、改变解释的反面论证(重要)**:随机特征仍可能支撑"保留一个
结构上不同的旧屏"这类**视觉新颖度启发式**——**这恰好解释了我方观察到的
recency_mass 从 0.57 激进降到 0.26**:selector 学到的可能是真实的
新颖度规则,只是该规则对任务成功没有帮助。此前我方把这个位移读作
"学到了东西但没转化为性能",现在有了更具体的机制解释。

**结论修正(必须写进结论文档)**:先前"selector 学习未获支持"的表述过强。
正确表述是——**我们从未真正检验过"任务条件化的语义记忆检索"这一假设**;
被检验并被否定的,只是"64×64 灰度随机特征 + 稀疏 50 步 credit
assignment 下的微型 RL 策略能否胜过 recency"。

## 执行顺序(定稿)

1. **反事实帧效用探针**(离线,executor 前向,300-1000 个状态):
   先答"executor 到底在不在乎给它哪些帧";
2. 若敏感度为真 → **换 executor 视觉塔特征 + 空间池化 token +
   query-conditioning**,打分头 1-3M;
3. **在该版本明确欠拟合之前,不碰 selector 规模**;
4. 若探针显示 executor 对历史帧不敏感 → 问题不在 selector 而在
   executor 的历史利用方式,方法主张需重写。
