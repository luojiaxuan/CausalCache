# 语义摘要检索式记忆:方法设计草案(2026-08-31,luojiaxuan 提出)

> 记录动机:当前 selector 路线经外审判定存在两个结构性缺陷(表示残废、
> 非 query-conditioned),而本方案从另一条路径绕开它们。先落盘防遗忘,
> 待探针(§4)给出上界后再决定是否投入实现。

## 1. 触发这个设计的两个事实(已代码核实)

**事实 A:历史截图是 before-action 的。**
`protocol._turn_frame` 取 `turn["observations"]` 的图,而 observation 是
agent 做决策**之前**看到的屏幕。故 turn *i* 的图 = 执行 action *i* **之前**
的状态;**"动作 i 的后果"存在 turn i+1 的图里**。

**推论(当前实现的时序错位)**:selector 选中 turn *i* 的帧时,给 executor
的是"动作 i 执行前"的画面。若模型想知道"我刚点开的发票里写了什么",
它需要的是 **i+1** 的帧。**现行选帧在时序上就取错了对象。**

**事实 B:折叠进 context 的 summary 只含意图,不含观察。**
实测一条真实轨迹的 conclusion 字段:
```
step 1: "Click on the Files app icon in the middle row"
step 2: "Click on the invoice.pdf file to open it."
step 3: "Navigate back to the home screen"
```
全部是"我打算做什么",**没有一个字是"我看到了什么"**。因此模型翻自己的
历史时知道"第 2 步点开了 invoice.pdf",但**发票金额从未进入文本通道**,
该事实只存在于第 3 步的截图像素里。这直接解释 §4.11 的观察:
CheckInvoice 类任务走到后段即抓瞎。

## 2. 方案:语义定位 → 图像恢复 → 二次 attention

```
当前决策缺什么信息(query)
        ↓  ① 在 summary 文本上检索(语义空间,低维、模型自生成)
定位到"哪一步可能产生了该信息"(如 step 2 点开了 invoice.pdf)
        ↓  ② 时序修正:取该动作的 post-action 帧(turn 3 的图)
恢复该帧进入上下文
        ↓  ③ 二次 attention(executor 在像素上精读)
产出动作
```

**与现行 selector 的本质差异**

| | 现行 selector | 本方案 |
|---|---|---|
| 检索在哪个空间 | **像素**(64×64 灰度 + 冻结随机 MLP) | **语义文本**(模型自生成的 conclusion) |
| 是否 query-conditioned | **否**(只吃候选帧特征 + 步位置) | **是**(query 就是"当前缺什么") |
| 取哪一帧 | turn *i*(**action 前**) | turn *i+1*(**action 后**,即后果) |
| 需要新视觉编码器 | 是(且当前的已被判死) | **否**(检索在文本上做) |

**三点优势**:① 绕开被外审判死的表示瓶颈——不需要在残废的像素特征上
判断"这张图里有没有发票金额";② 天然满足外审指出的 query-conditioning
要求;③ 修正了时序错位。

## 3. 已识别的设计约束

**PL 逐帧打分的可加性假设不成立(luojiaxuan 指出,我方认同)。**
现行 `slate_logprob` 是逐帧独立打分、按序联乘,数学上假设两帧价值可加。
但真实任务可能需要**两帧对照**才有价值(如"核对购物车价格与发票是否
一致"),单独任一帧都无用。**因此新方案的选择器必须是组合感知的**,
不能沿用逐帧打分再联乘的结构。探针(§4)会直接量化交互效应大小。

**待解问题(实现前必须回答)**
- summary 的语义粒度是否足以定位?现有 conclusion 只有意图,可能需要
  在生成时additionally 记录"观察到什么"(改 prompt 或加一个轻量总结步);
- 检索器由谁充当?可选:executor 自身(通过工具调用自取)、独立小模型、
  或纯规则(关键词/实体匹配);
- 恢复几帧、恢复后是否替换而非追加(上下文预算);
- 若被检索的帧不在 B 预算内,是否允许动态扩张。

## 4. 前置探针(先跑,决定是否投入)

**双帧枚举的 oracle 上界探针**——不需要 ground truth,枚举 C(8,2)=28
种双帧组合,取记录动作的归一化 token 对数概率:

| 量 | 含义 |
|---|---|
| `u_recency` | 两个最近帧(现行默认) |
| `max` over 28 组合 | **oracle 双帧上界** |
| `max` over(固定 recency + 换另一槽,7 种) | oracle 单帧 |
| 双帧上界 − 单帧上界 | **交互效应的价值** |

三路分诊:`u_j` 几乎不变 → 整条记忆路线无上界,方法主张需重写;
`max` 不高于 `u_recency` → 帧选择无上升空间;`max` 显著更高 →
信息确实在历史帧中、只是提不出来,**本方案的天花板即由该差值给出**。

**对照两个模型**:GUI-Owl-1.5-8B-Instruct(经 GUI SFT+RL,训练时只见过
连续历史窗口)vs 原始 Qwen3-VL-8B-Instruct(未经 GUI 塑形)。若后者的
上界显著更高,即量化了"GUI-Owl 被连续历史训窄"这一判断
(luojiaxuan 提出,替代外审原建议的随机换帧敏感度测试)。

只需 executor 前向,不需环境 rollout。

## 5. ★★ 探针结果(2026-08-31 执行,§4 设计的实测)

80 个状态 × C(6,2)=15 双帧组合 + recency 基线,候选帧全取 post-action;
GUI-Owl-1.5-8B-Instruct 与原始 Qwen3-VL-8B-Instruct 各跑一份;
仅 executor 前向,未占训练卡。

| 指标 | GUI-Owl-1.5(经 GUI SFT+RL) | Qwen3-VL(原始) |
|---|---|---|
| 组合间 logprob 跨度(中位) | **0.388 nats** | 0.438 nats |
| **oracle 双帧 − recency** | **+0.142**,95%CI [+0.111, +0.173] | +0.117,CI [+0.090, +0.144] |
| oracle 优于 recency 的状态占比 | **85%**(68/80) | 84%(67/80) |
| oracle 单帧 − recency | +0.056 | +0.024 |
| **交互效应(双帧 − 单帧)** | **+0.087(占收益 61%)** | **+0.093(占收益 79%)** |

### 四条结论

1. **executor 确实在乎给哪些帧**。跨度 0.39-0.44 nats 远非零,排除
   "executor 对历史帧不敏感"这一分支(外审曾把它排在参数量之前)。
2. **表示瓶颈坐实**。oracle 显著优于 recency(CI 下界 +0.111 > 0),
   **85% 状态存在比 recency 更好的组合** —— 信息确实在历史帧中,
   是当前 64×64 灰度随机特征的 selector 提不出来。**本方案(§2)由此
   获得一个非零的、可追的天花板。**
3. **★ PL 可加性结构被证伪(luojiaxuan 预判命中)**。交互效应占 oracle
   收益的 **61%(GUI-Owl)~79%(Qwen3-VL)**。现行 `slate_logprob` 的
   "逐帧独立打分 + 按序联乘"在数学上**无法捕获大部分收益** ——
   **换再好的视觉特征也救不了这个结构**,选择器必须改为组合感知。
4. **"GUI-Owl 被连续历史训窄"未获支持**(与预期相反)。GUI-Owl 的
   oracle 收益(+0.142)**略高于**原始 Qwen3-VL(+0.117),跨度亦相当。
   回到原始 Qwen-VL 做探针无额外诊断价值,该分支可关闭。

### 限制声明

+0.142 nats 是**动作 token 对数概率**的提升,**不等于端到端成功率提升**。
它证明"更好的帧使正确动作更可能被生成",但从 logprob 到成功率之间隔着
50 步的累积与环境随机性。**此上界是必要条件的证据,不是收益的保证。**

### 对方案实现的直接约束(由结论 3 导出)

选择器不能是"给每帧打分再取 top-B"。可选结构:
- 对候选**组合**打分(B=2 时 C(n,2) 个组合,n≤50 仍可枚举);
- 或自回归式选择:选完第一帧后,**以第一帧为条件**再选第二帧
  (与 PL 的形式相同但**打分函数必须接受已选集合作为输入**,
  而非现行的逐帧独立评分);
- 或用 set-transformer 类结构,让候选之间可以互相 attend。


## 6. oracle 选择模式分析(探针数据的二次挖掘,新架构的设计输入)

问题:最优帧组合有可学的**位置模式**吗?若有,便宜的启发式即可;若无,
必须靠语义理解。候选槽 0=最早(离当前最远) … 5=最晚(最近)。

| 槽 | GUI-Owl 被选频次 | Qwen3-VL |
|---|---|---|
| 0(最早) | 8.8% | 15.0% |
| 1 | 21.9% | 13.1% |
| 2 | 16.2% | 13.8% |
| 3 | 15.0% | 15.0% |
| 4 | 15.6% | 15.0% |
| 5(最近) | **22.5%** | **28.1%** |
| *均匀期望* | *16.7%* | *16.7%* |

**三条读数**:

1. **没有强位置先验**。最高频的槽也只有 22.5%/28.1%,离均匀(16.7%)不远;
   最常见的具体组合(`4+5`)只占 12/80 = 15%。**没有任何固定组合能主导**
   → **便宜的位置启发式不够,必须靠内容理解**。这是对本方案(§2 语义
   检索)最直接的支持。
2. **recency 在 15 个组合中排名中位 = 6**,即平均有 5 个组合比它好 ——
   它不是最优,但也不差(中位偏上)。**这解释了 recency 为何如此难打败**。
3. **最近帧确实常在最优组合里**:含槽 5 的比例 45%(GUI-Owl)/ 56%
   (Qwen3-VL),但**并非总是**。

### 由此导出的具体架构建议

**双槽异构设计**:
- **槽 A 固定为最近帧**(post-action 的最新一张)—— 它出现在 45-56% 的
  oracle 组合里,是稳定的价值来源,不必让模型去学"要不要带上最近的";
- **槽 B 走语义检索**(§2 的 summary 定位 → post-action 帧恢复)——
  这一槽承担"因状态而异"的那部分,正是位置启发式抓不住、也正是
  当前 selector 完全失败的部分。

这个划分还有一个工程上的好处:**把组合爆炸降了一维**。§5 结论 3 指出
选择器必须组合感知(交互占收益 61-79%),而固定槽 A 后,槽 B 的选择
天然是"以槽 A 为条件"的 —— **无需枚举 C(n,2),只需在给定最近帧的前提下
选一帧**,复杂度回到 O(n),同时保留了条件依赖(不是可加假设)。


## 7. ★ 离线验证:语义检索的前提条件不成立(2026-08-31)

**做法**:不改任何在线组件。复用探针已测出的 logprob 真值表(每状态 15
个双帧组合),让纯文本检索器去"选"组合,再查表看它选中的值。
判据 = 检索收益 / oracle 收益。

| | GUI-Owl | Qwen3-VL |
|---|---|---|
| oracle 收益 | +0.1408 | +0.1131 |
| **词重叠语义检索** | **−0.0113** | **−0.0184** |
| 对照(最近帧 + 随机) | −0.0098 | −0.0332 |
| 可实现比例 | **−8%** | **−16%** |

**检索器等价于随机**(−0.0113 vs −0.0098)。两种解释必须分开:
A. 检索器太弱;B. summary 里没有定位信号。

**分诊实验**:看 oracle 选中帧的 conclusion 与 query 的相关性,是否高于
未选中帧。

| | 相关性 |
|---|---|
| oracle 选中的帧 | 0.1651(n=154) |
| 未被选中的帧 | 0.1430(n=308) |
| 差 | **+0.0222,z=+1.23(不显著)** |

**结论:解释 B 成立 —— 现有 summary 的定位信号方向为正但强度不足。**
根因即 §1 事实 B:conclusion 全是"我要做什么"(`Click on the invoice.pdf
file to open it`),而检索需要的是"我看到了什么"(`发票金额 128 元`)。
模型知道自己第 2 步点开了发票,却**无从判断那一步是否产生了它此刻需要
的信息**。**无论检索器多强,都提不出不存在的信号。**

### 这不否定 §2 架构,而是给它加了一个前置条件

链路里 `[在 summary 上检索]` 这一环当前是断的。三条修法(成本递增):

1. **改 prompt 让 conclusion 带观察** —— 最便宜;但改变 executor 输出
   分布(需重验 204 例 parity),且历史轨迹的 summary 格式会不一致;
2. **加轻量旁路总结步** —— 每步后用小模型对 **post-action 截图**生成
   一句"这一步之后看到了什么"。不动 executor 输出(parity 锚点保住),
   可离线批量补做历史轨迹,产出的观察摘要直接作为检索索引。**我方倾向**;
3. **索引改用视觉特征** —— 绕回被判死的表示问题,除非用 executor 视觉塔
   特征,成本与方案 2 接近而收益不明。

**方法论价值**:该验证仅用已有数据、零 GPU 增量,却在实现前就查出了
架构的断点。若直接实现完整链路,会在检索不工作后陷入长时间 debug,
且极易误归因为"检索器设计不好"而不断加大模型。

## 8. ★ 修正后的重测(探针 v2,2026-08-31)

§5–§7 的数字全部作废,以下为修正 off-by-one 之后、同一批 80 状态的重测。

### 8.1 天花板不降反升

| | GUI-Owl v1→v2 | Qwen3-VL v1→v2 |
|---|---|---|
| oracle 双帧 − recency | +0.142 → **+0.187** | +0.117 → **+0.177** |
| 95%CI | [+0.162, +0.212] | [+0.144, +0.209] |
| 优于 recency 的状态 | 85% → **98%** | 84% → **90%** |
| 随机双帧 − recency | −0.069 → **+0.026** | −0.114 → **−0.015** |

方向与预期相反,原因清楚:v1 把目标动作**执行后**的画面当作当前帧喂了进去,
模型已经看到结果,对历史的需求被人为压低。去掉泄漏后,历史帧的价值显现。

**同时暴露:recency 是个弱基线。** 修正后随机双帧与 recency 基本打平
(+0.026 / −0.015),即"取最近两帧"这个线上默认几乎没有优于随便取两帧。

### 8.2 两帧价值可加吗——判决:部分可加,代价过半

用最小二乘对每状态拟合 `v(a,b) ≈ m_a + m_b`:

| | R² 中位数 | R² 均值 | R²<0.5 的状态 |
|---|---|---|---|
| GUI-Owl | 0.747 | 0.706 | 15% |
| Qwen3-VL | 0.742 | 0.720 | 12% |

可加结构解释约七成方差。但**选择精度**上代价明显:用留一法估边际再按加和
选组合,只拿到 oracle 的 **50%(GUI-Owl)/ 41%(Qwen3-VL)**。
(样本内估边际会得到 86%/81%,是乐观偏差,不可引用。)
**结论:PL 的可加结构不致命,但要付出约一半可达收益的代价。**

### 8.3 ★ 相似度检索是错的方向(反向显著)

A/B 实验:同一检索器、同一候选集、同一真值表,只换 summary 内容。

| | 收益 | 占 oracle |
|---|---|---|
| oracle | +0.1872 | 100% |
| 随机双帧 | +0.0264 | 14% |
| A 现系统的意图式 conclusion | +0.0184 | 10% |
| B 新生成的观察式 caption | +0.0033 | 2% |

两组都在随机线上或以下。但该实验**被检索器污染**:LLM 检索器有强近因偏好
(`x_5` 组合占 65/80 与 55/80,15 种组合只用到 8–9 种),测的是检索器能力
而非 summary 信号。

改用**不依赖检索器**的统计判据——oracle 组合内的帧,其 summary 与
query(goal + 当前动作)的 IDF 加权词重叠是否更高:

| | oracle 帧 | 非 oracle 帧 | 差 | z |
|---|---|---|---|---|
| A 意图式 conclusion | 0.1986 | 0.2429 | −0.0444 | −1.63 |
| B 观察式 caption | 0.0680 | 0.0866 | −0.0186 | **−2.21** |

**两组都是负的,观察组显著。** 真正有用的帧,其 summary 与当前目标的文本
相似度**更低**。

**这不否定 §2 的架构,而是纠正了它的检索判据。** 原始表述是"从当前要执行
的动作**所缺少的信息**定位 summary";而 §5–§7 的实现检索的是"与当前动作
**相似**的 summary"——恰好相反。数据说:有用的帧携带的是**互补**信息,
不是同类信息。相似度不仅无效,还轻微反向。

**§7 的"summary 缺定位信号"结论需改写**:不是信号不存在,而是我用错了
度量。观察式 caption 也没救回来(2% of oracle),因为 8B captioner 产出的
是"这是主屏,有若干图标"这类低区分度描述,并且判据本身就选错了方向。

### 8.4 由此得到的可执行路线:用 oracle 标签监督 selector

探针本身就是一台**每帧/每组合价值的测量仪**,只需 teacher-forcing 打分,
不需要跑完整 episode。既然"什么帧有用"无法用相似度写死,就直接**把 oracle
测出来当监督信号**训练 selector,而不是只靠 RLOO 穿过 episode 回报去学——
后者方差极大(§4.16:P1–P3 超过一半梯度被裁掉的是记账误差)。
待评估项:标注成本(每状态 15 次打分)、覆盖多少状态才够、以及与在线 RL
的结合方式(预训练 selector 后再联合微调)。

## 9. 槽位设计判决:B 张全任选,序贯条件选择(2026-09-01)

§6 由 v1 表导出的"固定一张最近帧 + 一张检索"双槽先验,在 v2 表上**反转**:

| 候选按时间排 0=最老..5=最近 | GUI-Owl | Qwen3-VL | 均匀期望 |

任务设定)被选最多;远帧(6–10 步)选中率是均匀的 1.6–2 倍。机制:当前帧

**定稿设计:序贯条件选择** `q0=f(goal, 折叠历史文本, 当前帧)→选c1; q1=g(q0,c1)→选c2; …`——query 由决策时的**全部** context 构成(goal ⊕ 到当前为止各步 conclusion/tool response 的折叠文本 ⊕ 当前帧真特征);"缺什么"是相对已有 context 定义的,漏掉折叠文本会去检索文字里已写明的信息
到预算为止。性质:(a) 第二张条件于第一张,直接针对非可加性(§8.2:可加式
只拿到 oracle 的 50%/41%,损失正出在独立打分);(b) 对 B 无感,B=2/4/8 同
机制不同截断,零架构改动;(c) 近因偏好若有价值是可学行为而非硬约束,
"固定最近帧"降级为 ablation 行。

**新 selector 输入契约**(修正 §2 的实现缺陷——现役 selector 只收历史帧
缩略图 + step 整数,看不到当前帧与 goal,"从当前缺什么出发 query"不在其
假设空间内):query 端 = goal ⊕ 折叠历史文本 ⊕ 当前截图真特征;候选端 = 该帧真特征 ⊕ 该步自己的 conclusion 文本 ⊕ 位置编码——帧与其文字摘要绑定打分,检索的正是"文字摘要没说够的部分";c1 连同其文本一起进入 q1 的条件。各帧真特征
(executor 视觉塔或 SigLIP,冻结、rollout 时按帧缓存);打分 = query 条件
下的 cross-attention,序贯展开。

### 25.1 曲线读数

heldout 锚点 = 固定 20 个从未参与训练的任务,executor 冻结,每 3 个回合用当前
selector 权重评一次;基线是同一批任务下 recency 策略(取最近两帧)的一次评测。

| 点 | 策略 | 成功/判定 | 成功率 |
|---|---|---|---|
| 基线 | recency | 3/19 | 15.8% |
| r3 | learned | 1/19 | 5.3% |
| r6 | learned | 2/15 | 13.3% |
| r9 | learned | 4/19 | 21.1% |
| r12 | learned | 5/18 | 27.8% |
| r15 | learned | 6/19 | 31.6% |

读法:每点 n≈19,二项标准误约 10pp;末点 6/19 对基线 3/19 的 Fisher 精确检验
p≈0.45,**单点不显著**。证据在趋势:5 个点严格单调递增,若各点可交换(纯噪声)
则概率为 1/5! ≈ 0.8%。基线本身只测过一次,其噪声未量化。

训练域对照(同任务配对,消掉每回合抽到哪些任务的混杂):两半都出现的 25 个任务,
r1–8 均值 0.293(n=270)vs r9–16 均值 0.245(n=249);首次/末次出现配对 39 个任务
涨/跌/平 = 7/7/25。**训练域不涨、heldout 涨**,两种解释待判:
(a)25/39 个重复任务两次出现成功率完全相同,说明训练域大半任务由 executor 的
天花板/地板决定、selector 没有杠杆,heldout 20 题恰好在可控子集上占比更高;
(b)heldout 曲线是噪声。判决手段:r18/r21 继续采点;**补测一次 heldout 的
recency 基线**(第二个基线样本,量化基线自身噪声)。

### 25.2 分词器并发 bug(自训练启动起一直存在)

服务日志 558 次 `RuntimeError: Already borrowed`(09-02 17:29Z 起至今),
HF fast tokenizer 非线程安全,`ThreadingHTTPServer` 并发请求同时进入分词
(`proc(images=...)` 内部与 `tok(...)` 都走它)即触发。锁 `_lock` 原本只护住了
能量头前向。

影响量化:成功决策 69,100 条,请求级错误率 0.8%;但错误集中在回合开头三槽并发
(round_16:tag0/1/2 各 8/6/6 次,tag3–7 共 5 次),每次错误 = agent 该步抛
HTTPError、episode 中止、mw-eval 重开一次(目录 24 个 vs 结果 7 个)。后果:
(i)重试拖长回合墙钟;(ii)决策记录键 `gmd5|tag` 把中止尝试的步骤与重试尝试的
回报绑在一起,是**噪声不是偏差**(回报与这些步骤的选择无关);(iii)锚点的
learned 臂承受额外崩溃而 recency 臂不调用服务,**偏差方向对 learned 不利**
(曲线是保守的);(iv)r6 只判定 15 题,即崩溃+重试撞上 5400s 整体超时。

修复:`_tok_lock` 一把锁护住两处分词调用;文件已替换,下次服务重启生效。

### 25.3 服务 RSS 泄漏与周期重启(trainer v9)

`sglang-omni-jaxan-rls` 宿主 RSS 23h 达 155GB(≈6.7GB/h;宿主 2TB、可用 1.36TB,
不构成险情,但按"长命推理服务不跨段复用"的规矩处理)。有界缓存
(`_fcache` 4000 / `_tcache` 8000 条,合计 <100MB)不是来源,疑为多线程
glibc arena 膀胀;不再追因,用重启节奏兜住。

设计:trainer 的边界重载路径(`boundary_reload`)每 6 个版本先
`docker restart` 服务再 `/reload`(最新权重 + 新版本号)。安全性由两条保证:
只在 `want_reload` 旗子在场时重启——编排器的 ROUND_DONE 屏障正等它消失,重启
期间不会有新 tag 起;版本号≡0 (mod 6) 对应回合≡2 (mod 3),与锚点评估
(ROUND_DONE≡0 (mod 3) 起,实测 47 分钟)错开。重启后服务从 pv 文件读到旧
版本号且回到预训练权重,紧接的 /reload 把两者一起纠正;失败则版本号不落盘、
下一回合数据整体标旧版本被过滤,监控行出 `FAIL`。首次触发点 ROUND_DONE 17。

为什么不放编排器:编排器轮换有竞态——ROUND_DONE 打印后毫秒级发下一轮 tag,外部
`pkill` 必然滞后;回顾 rotate3 切 v4 时,round 8 的前 3 个 tag 可能被旧/新
编排器双发到同一批模拟器(returns 计数正常,未见明显异常,**记为已知瑕疵**)。
trainer 无状态(游标/版本号/权重都在盘上),回合中途重启零成本。

决策日志:问题=服务泄漏怎么处置;默认=trainer 边界周期重启;理由=唯一天然
无竞态的钩子点;回滚=`SEL_RESTART_EVERY=0` 重启 trainer 即关闭;外审=运维
修复、答案明显,未发审。

### 27.2 结果(n = 3,403 四条件齐全)

| 条件 | AMS | tap | text | long_press |
|---|---|---|---|---|
| none(文本历史) | 50.7% | 57.8 | 50.8 | 12.3 |
| **recency2** | **57.0%** | 64.6 | 57.2 | 11.8 |

  = **31.4%**,与随机远帧的 31.6% 相同。
- 四条件取并集的"oracle" 66.1% 对 recency2 57.0% 看似有 9pp,但"只有 gold 对"的步 90 个
  对"只有 random 对"的 72 个——并集增益主要是采样随机性,不是记忆信息。

### 27.3 判读

冻结的 GUI-Owl-1.5-8B **不能利用"替换最近帧"的远程截图**:标注为决定性的来源屏幕,对它
而言与随机远帧无异;它真正依赖的是最近帧提供的状态追踪(recency2 比 none 高 6.3pp)。
这与 §26.2 训练标签"24.4% 上下文中某帧对能救回"并不矛盾——那里的正确对可以包含最近帧;
也直接回答了用户 09-01 的问题"executor 能不能理解不连续的图":在这个尺度和提示格式下,
**不能**。剩余的假设空间只有一种:**保留最近帧 + 追加一张远帧**(第二批条件
rec1_gold1 / rec2_gold1);同时用去文本消融(none_notext / gold_notext / recency2_notext)

### 27.6 MemGUI 基线的运维收敛(2026-09-03 22:00 PT):三层根因与最终协议

三层根因(逐层证实):
1. **宿主 inotify 配额**:`fs.inotify.max_user_instances=128` 按 UID 计,所有容器均为 root
   共享;宿主 71 个 root 容器时我们第 8 台后端里 adb 起不来(`failed to create inotify fd:
   Too many open files`),模拟器恢复后 adb 报 `device unauthorized`。管理员侧一行 sysctl
   可解,已请用户转达;在此之前我方最多 5–7 台后端。
2. **官方 `mg env run` 起的容器无 init**:PID 1 是 `tail -f`,模拟器崩溃后成 `<defunct>`,
   容器内恢复脚本永远 `in_progress`。改为按其 dry-run 原命令自起并加 `--init`。
3. **runner 的自愈路径**:显式 `--aw-host` 时不知道容器名(不能自愈);知道容器名后又会
   对起不健康的后端**无限重建**(重建出的容器无 init),病后端以 0 秒假完成吞掉任务
   (臂 B 一轮 96 题里 76 题为假完成)。

最终协议(`memgui_pass_loop.sh`):我方接管后端健康——每轮开始删掉不健康/无 init 的后端、
带 `--init` 重起到 5 台、等 healthy;计算该臂**轨迹为空**的任务只跑这些(runner 按前缀自动
发现,并发 = 健康后端数);最多 4 轮直到无缺失。判分:in-run judge 在 7 路并发下有 429
(臂 A 86 次、43 题判错),统一用 `memgui_rejudge.py --only-errors --no-resume` 低并发补判;
runner 重试留下的 `<task>_backup_<ts>` 目录不是评测单元,跳过。分数口径:每臂 128 题,
成功数 / 128(缺失即失败)与 成功数 / 有效判定数 两列并报。

臂 A(官方默认历史窗)当前:7 题成功,41 题判错待补判,其余判定失败。
