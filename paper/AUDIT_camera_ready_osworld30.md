# 紧急:camera-ready 的 30 步主结果与实测全量不符

**结论:摘要与 Table 1 主行引用的 OSWorld 30 步 `46.7 vs 42.4 (+4.3)` 来自一次
未跑完的实验。跑满 361 后两臂都低得多,且差值符号反转为 −0.55pp。**

## 对照

| | camera-ready | 实测全量(各 361,同一评测器与名册) |
|---|---|---|
| Recent-4 @30 | $42.4\%$ | **36.01%** |
| \method{} @30 | $46.7\%$ | **35.46%**(全 H200 干净口径) |
| Δ | **+4.3pp** | **−0.55pp**,CI95 [−4.71, +3.60],p=0.62 |

数据出处:
- Recent-4:`data/results/osworld30_horizon_v1/osw30_recent_h0{0,1}.json`(361);
- \method{}:`data/results/osworld_sel30_clean_v1/per_task_sel30_clean.json`(361);
- 归约:`code/scripts/merge_aries_repair.py`。

## 这个数是怎么来的、又是怎么反转的

`46.7/42.4` 写入 main.tex 于 commit `05d697a`(07-29 04:34,分支
`jaxan/trusting-zhukovsky-00d2bf`)。当时那轮 30 步跑批**尚未完成**。随数据补齐:

| 时间 | 状态 | Δ |
|---|---|---|
| 07-29 04:34 | 写入论文 | **+4.3pp** |
| 07-29 08:48 | 四机复现归档 | −3.1pp |
| 07-29 09:03 | 361/361 定稿 | −2.8pp |
| 08-01 | 剔除 A6000 主机污染后 | **−0.55pp** |

符号在数据补齐后立刻反转,之后再没回正。

## 为什么当时的中期数偏高

15/30 步的 OSWorld 跑批里,**先完成的任务系统性偏易**(短 episode 先结束)。
本项目已因此误判六次,其中这一次进了论文。相关记录:
`data/results/teacher_ab_v1/README.md`(规则:任何闭环比较必须等两臂跑满全量)。

## 另有一处需要复核

camera-ready 的 Table 2(OSW@15 列)写 \method{} $= 33.3$,而
`data/results/osworld_verified_closed_loop/README.md` 的五臂终表是:

| 臂 | 成功率 |
|---|---|
| 冻结 B0 | 19.94% |
| frozen + Recent-4 | 32.69% |
| HGKV + Recent-4 | 32.96% |
| **CausalCache-LA(单遍)** | **34.07%** |
| CausalCache-P(两遍) | 32.69% |

论文的 33.3 与其中任何一臂都对不上(此前版本写的是 34.1,对应 LA 臂)。
**需要确认 33.3 的出处**,否则 Table 1 的 15 步行 `33.0 / 33.3 / +0.3` 也无据。

## 还必须知道的:这个基准在这个口径下测不出 ±4pp

`data/results/indomain_gap_v1/ROOT_CAUSE.md` §5 与
`data/results/indomain_twoarm_v1/README.md`:

- 两个**在 98% 的步上发出相同动作**的臂,任务级翻转 **14.4%**、差 **−3.88pp**;
- 同一个 Recent-4 臂在三个时间窗分别是 **32.96% / 30.47% / 29.92%**(跨轮差最大 3.0pp);
- 两轮同批双臂 n=722 仍只能给出 +0.83pp(p=0.24)。

**推论:任何单轮 OSWorld 15/30 步的 ±4pp 以内差异都不构成证据**,无论正负。
因此不能简单地把 `+4.3` 换成 `−0.55` 然后声称"同域有害"——正确做法是承认
**这个基准在单轮口径下没有分辨这个量级的能力**。

## 建议的修改方向(三选一,需你定)

1. **撤回 30 步主结果,恢复 15 步为主**,并加噪声地板说明:
   同域两臂在任何已测横线(15/30/50/100)上都不可区分,而 mobile 上有明确增益。
   叙事从"同域也涨"改为"**同域是可用性验证,分配增益由 mobile 承担**"。
   这是与现有全部数据一致、且最省改动的方案。
2. **保留 30 步但改为真实数字**(36.0 vs 35.5,−0.55pp)。诚实,但会让主表出现
   一个负号,且仍在噪声内,读者不易解读。
3. **多轮做实后再定**:同域需 ≥3 轮全量才能判定 ±3pp;若要在 camera-ready
   里保留任何同域分配主张,这是唯一严谨路径(约 4 小时机时)。

**我的建议是方案 1**,并把 `docs/indomain_defense_draft.md` 里那三步论证
(先立噪声地板 → 再用 oracle 余量证明头寸存在 → 说明 B=4 是最难展示的工作点)
接到限制段,把"同域不涨"从弱点转成方法论贡献。
